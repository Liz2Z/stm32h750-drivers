# 显示与采集可靠性、局部刷新踩坑记录

## 1. NOLOAD 缓冲区不能先取得已初始化引用再清零

原 `init_frame_buffer()` 对 `MaybeUninit` 调用 `assume_init_mut()` 后再 `fill(0)`。
即使最终写满整个数组，取得引用时内存还没有初始化，已经违反 Rust 的安全约束。

修复：先通过原始指针 `write_bytes` 初始化 AXISRAM，再创建数组引用。
缓冲区只能领取一次，由 `DisplayDriver` 独占，绘图不再重复创建全局可变引用。
AXISRAM 位于 D1 域。当前实际传输是有界阻塞 SPI，没有启用硬件 DMA。

## 2. 传感器共享总线，不应销毁驱动或绑定成功分支

原流程只有 AHT20 读取成功，才把总线交给 BMP280。
AHT20 断开时，正常的 BMP280 也停止更新；BMP280 的错误又被静默忽略。

现在由 `acquisition::Sensors` 持久保存驱动状态，两者逐次借用同一个 `&mut I2C`。
每个传感器独立读取、独立重试初始化，BMP280 的校准参数保持在同一个实例中。
此前通过 `release/attach` 维护总线所有权的方式已被替代。

BMP280 未检测到器件必须返回 `DeviceNotFound`，不能返回初始化成功。
零值或全一的关键校准参数会被拒绝，初始化后等待首次转换，并拒绝复位态原始值。
AHT20 初始化后复查校准位；读取时也检查数据帧的 busy/calibrated 状态。

## 3. 零度是真实数据，不能用作未初始化标志

原统计逻辑在最高/最低值为零时重新初始化，导致 `0°C → 5°C` 的最低值变成 `5°C`。
现在根据有效样本计数识别首次采样，非有限值不会污染历史。

没有成功样本时显示 `--`；首次采集前显示 `WAIT`，采集失败显示 `ERROR`。
已有有效样本后失败则保留旧值并显示 `STALE`，同时保存最后成功的硬件时间戳。
温度和湿度继续使用各自的数据对象和历史记录。

## 4. 上层重试次数不能限制 HAL 内部死循环

HAL 0.16 的阻塞 I2C 以及原 SPI 等待内部可能无限轮询。
在外围写 100 次重试，无法打断已经卡住的单次调用。

I2C1 现在保留 HAL 的引脚、时序初始化，通过 PAC 执行有期限的事务：
一次事务期限 10ms；故障时尝试 STOP（最多 1ms），清标志并重新启用控制器。
SPI 使用非阻塞 FIFO 收发，每块发送/完成等待上限 100ms，错误向上传递。
事务出错会释放 CS，后续重新初始化屏幕并重发整帧。

控制器恢复不能保证解除外部器件持续拉低 SDA/SCL 的物理故障；这类故障会持续返回超时，
需要检查连线、供电和上拉。正常采集与控制器超时恢复已实板验证，见第 9 节；
持续拉低总线的物理故障仍需单独验证。

## 5. 绘制帧缓冲不等于刷新屏幕

卡片仅创建一次。更新时绘制动态区，通过 `FlushTarget` 明确刷新。
三张卡片的动态区各为 98×115，全部变化时像素数据为 67,620 字节，
原整屏为 153,600 字节，减少约 56%（不含窗口命令、独立底栏刷新）。
内容不变时跳过卡片传输。窄矩形的多行会打包进同一传输块，避免逐行启动 SPI。
刷新区域会裁剪，空区域直接跳过，坐标计算避免 `u16` 加法溢出。

TIM2 按 1MHz 自由运行；采样以 5 秒期限调度，使用回绕减法，错过期限后跳过积压任务。
它不再用主循环次数推算时间。32 位计数器约 71 分钟回绕，必须在一次回绕内轮询调度。

原 ESP8266 通信逻辑保留，但默认关闭启动和主循环重试（`ESP8266_ENABLED = false`）。
其阻塞流程会推迟主循环，定时器调度不会抢占它，不能直接重新启用。详见第 10 节。
本次没有更改 ESP8266 协议，也没有引入硬件 DMA。

## 6. macOS 主机测试不能链接 MCU 中断向量

第一次执行主机测试时，STM32 PAC 的 `rt` 特性产生 `.vector_table.interrupts`，
该 ELF section 名称不符合 macOS Mach-O 格式，LLVM 编译失败。

修复：把 HAL、Cortex-M 和 panic-halt 放到 Cargo 的 ARM 专用依赖区。
驱动解析、采集编排、UI 和调度在 `no_std` 库中共享，主机测试直接运行同一份代码。

验证入口：

```sh
make test   # 主机回归测试
make check  # 格式与默认配置 Clippy
make build  # ARM release 固件
```

回归测试覆盖设备缺失和恢复、独立采集、参考气压补偿结果、校准失败、忙状态期限、
零度统计、计时器回绕、矩形裁剪、跨行 RGB565 打包、SPI 超时和错误传递、
局部刷新与全屏绘制逐像素一致、刷新失败后的脏区域保留。

实板建议检查：冷启动、任一传感器拔插、I2C 卡线后的超时返回、横屏显示、
长期运行跨计时器回绕。主机测试不能代替对实际 SPI/I2C 时序的检查。

## 7. OpenOCD `open failed`：先检查 USB 是否识别调试器

2026-10-10 执行 `make flash`，固件构建和 BIN 转换成功，但 OpenOCD 在初始化
ST-Link 时返回 `Error: open failed`、`OpenOCD init failed`，未执行写入和校验。
随后检查 macOS 的 USB 设备列表，没有发现 ST-Link，也没有其他调试程序占用它。

这种情况发生在访问目标 MCU 之前，不应先归因于固件、Flash 布局或 SWD 时钟。
先确认 ST-Link 通过数据线连接电脑且被 USB 识别，再检查板卡供电、共地和 SWD 接线：

- ST-Link SWDIO → MCU PA13。
- ST-Link SWCLK → MCU PA14。
- ST-Link GND → 板卡 GND。
- 按实际探针的供电/参考电压要求连接，勿把 5V 接到 MCU 的 3.3V 电源轨。

macOS 可使用 `ioreg -p IOUSB -l -w 0` 检查 USB 枚举。
USB 转串口或其他芯片的内置 JTAG 设备，并不等于当前 Makefile 配置的 ST-Link。
识别到调试器后重新执行 `make flash`；必须看到写入、校验和复位成功，才能报告烧录完成。

## 8. 不应根据配色注释擅自改变现有视觉效果

原配色中传给 `Rgb565::new` 的部分分量超过 RGB565 范围，实际渲染效果与注释颜色不同。
第一次优化按注释转换成 RGB888，改变了用户原有的配色。这不是已获确认的显示需求，
已恢复原主题和底栏的实际颜色值。性能和可靠性优化应保持用户现有视觉效果。

原底栏从 y=210 开始，覆盖到卡片底部；10×20 字体也使三个状态字段互相覆盖。
底栏改为 y=220、高 20，使用 6×10 字体。默认只显示实际采样次数 `Samples`，
不显示未启用的 ESP/上传状态。ESP8266 通信代码保留。

## 9. 2026-10-10 实板验证

连接后 macOS 识别到 ST-Link（VID:PID 0483:3748，V2J18S4），目标电压约 3.30V。
通过 `make flash` 烧录，OpenOCD 确认 `Programming Finished`、`Verified OK`、
`Resetting Target`。最终固件构建前的 17 项主机回归测试、格式检查和 Clippy 均通过。

使用 `make debug` 和 ARM GDB 检查运行状态：

- 连续采集得到约 26°C、67%RH、1009.8hPa，三个对象均为 `Fresh`，成功时间戳持续推进。
- 在 `Screen::draw_sensor_updates` 中所有 `flush_rect` 返回成功后的 `clear_dirty`
  处命中断点，确认实板局部 SPI 刷新成功；SPI2 状态寄存器无错误，CPU CFSR 为零。
- 在一次采集结束后临时清除 I2C1 CR1 的 PE 位，模拟下一次事务无法推进。
  下一周期温湿度变为 `Stale`，气压仍为 `Fresh`；随后温湿度恢复为 `Fresh`，
  I2C1 PE 自动重新启用，CPU CFSR 仍为零。该测试验证控制器超时恢复及独立采集，
  不等同于拔插传感器或外部器件持续拉低 SDA/SCL。
- 从 AXI SRAM 读回 320×240 RGB565 帧缓冲并转换为 PNG，检查卡片文字、数值、
  历史图与底栏布局。帧缓冲检查和 SPI 返回成功不能替代对实物面板颜色、闪烁的目视检查。

以上为第一版验证，未充分确认连续采样周期。用户随后报告更新停滞，见第 10 节修复。
尚未执行长时间跨 TIM2 回绕运行及物理拔插/卡线测试。

## 10. 单次采集和 SPI 返回成功不能证明持续更新

用户反馈底栏长期停在 `Frame: 1`。GDB 实板调用栈显示主循环停在
`Esp8266::initialize → delay_ms(1500) → cortex_m::asm::delay(600000000)`，
CPU CFSR 为零。ESP 初始化和失败重试直接运行在采集循环中，阻塞期间所有显示更新都被推迟。
软件周期延时的实际耗时也不能仅由主频推算，不能将“有硬件期限调度”当作非阻塞保证。

当前任务只处理显示和采集，因此增加 `ESP8266_ENABLED = false`，默认跳过启动连接与
主循环重试，保留通信代码。屏幕启动等待改用 TIM2 延时。底栏 `Samples` 每次实际采样
递增一次，替代原先每次主循环递增、含义不明确的 `Frame`。

实板验证必须观察多个连续周期的采集时间戳、刷新成功和样本计数，不能只验证一次。
本机 ARM GDB 未启用 Python，批量断点验证应使用普通 GDB 命令文件。

修复版通过 `make flash` 重新写入并校验成功，17 项回归测试和 Clippy 通过。
连续命中 13 次局部刷新成功断点，采样计数从 18 增至 30，温湿度/气压均为 `Fresh`。
后 11 个成功时间戳间隔为 4,999,144～5,000,776µs；刚接入调试时的首个间隔
受暂停/恢复影响为 2.36 秒，不用于周期精度判断。SPI2 SR=0x1002，CPU CFSR=0。
随后再次读回画面，底栏已增至 `Samples: 49`，数值与历史图继续变化，原配色恢复。

## 11. 底栏刷新率应统计成功传输，不能统计主循环次数

底栏增加 `Refresh: x.xx Hz`，按最近一个已完成的 10 秒窗口统计内容更新。
一轮变化卡片全部传输成功记一次，显示故障恢复后整屏传输成功也记一次；
无脏区域、失败的传输和底栏自身刷新均不计入，避免刷新率被状态文字自身抬高。
它表示应用内容的实际更新频率，不表示 LCD 面板内部扫描频率或 SPI 理论吞吐量。

启动后第一个窗口完成前显示 `-- Hz`；仅每 5 秒采样、没有动画时约为 `0.20 Hz`。
一个完整窗口没有成功更新则显示 `0.00 Hz`。使用实际经过时间及回绕减法计算，
保留两位小数并四舍五入，避免定时抖动让 0.19999Hz 显示为 0.19Hz。
主机测试覆盖空闲窗口归零、计数器回绕、延迟轮询和舍入。

`make test` 的 19 项测试、`make check` 均通过，`make flash` 写入并校验成功。
实板连续 4 次刷新成功时，计数从 8 增至 11，统计结果均为 20 centihz（0.20Hz），
CPU CFSR 为零。随后读回帧缓冲确认 `Samples: 16` 和 `Refresh: 0.20 Hz` 并列显示，
无文字重叠，原配色保留。

## 12. 顶部动画使用独立期限与局部刷新（2026-10-11）

顶部空白区加入往返流光动画，每 50ms 尝试更新一次，只刷新 (5,3,310,14)，
每次像素数据 8,680 字节。卡片从 y=20 开始，底栏从 y=220 开始，互不覆盖；
继续使用原主题颜色。动画成功传输记入 `Refresh`，底栏自身仍不计入。

相位由硬件经过时间计算，晚到时跳过中间帧，不能补画积压帧阻塞采样。
尾迹使用延迟相位，转向时仍留在动画区域内，清除区域覆盖全部旧像素，避免残影。
TIM2 计数回绕通过增量累计处理。主机测试检查动画确实移动、绘制不越界、
跨回绕相位连续及错过整周期后的相位一致性。

传感器采集保持 5 秒期限，但仍有短暂同步等待，实际动画频率以底栏测量值为准。

验证：20 项主机测试、格式检查和 Clippy 通过；`make flash` 写入并校验成功。
实板未连续暂停前的 10 秒窗口测得 19.80Hz。连续四次采样计数 10→13，
成功时间戳间隔约 4,999,390～4,999,984µs，气压为 `Fresh`。
两次动画成功传输处读回的相位分别为 208,333µs 和 3,618,126µs，图像中光点位置不同；
SPI2 SR=0x1002、CPU CFSR=0。断点暂停会降低后续测量窗口的刷新率，不能据此推断正常运行卡顿。

## 13. 测速要排除调度限速和调试器暂停（2026-10-11）

新增 `display-bench` 编译特性，默认固件不包含测速代码。`make bench-flash` 使用
独立的 `target/display-bench` 目录构建和烧录，避免覆盖正常固件 ELF。
启动时先预热一次传输，再连续执行清帧缓冲 64 次、整屏传输 32 次、三张卡片传输
64 次、顶部小区域传输 128 次、清屏并传输整帧 32 次。没有 50ms 动画限速、传感器等待
或 ESP 通信，结束后保存结果并继续进入正常 UI。

使用 TIM2 的微秒计数记录每次成功操作的最短、最长、总耗时以及失败次数。
传输测试包含 RGB565 字节打包和窗口命令，不能把它当作纯 SPI 线上耗时；
整屏组合测试只包括纯色填充和传输，不包含视频读取、解码及复杂 UI 绘制。
GDB 读取时 `DISPLAY_BENCH_RESULTS.status` 必须为 2，计时过程中不要暂停 MCU。
平均帧率使用总成功次数除以总成功耗时，不能取最好一帧代表持续吞吐。

HAL 0.16 将请求的 SPI 时钟向下取到支持的二次幂分频。必须结合实际内核时钟与
SPI2 CFG1.MBR 计算 SCK，不能将 `.spi(..., 80.MHz(), ...)` 或 README 注释当作实测频率。
此处计算值来自时钟树和寄存器，最终电气频率仍可用逻辑分析仪确认。

第二阶段仅在测速固件内临时开启 I-Cache，预热后再测 64 次整屏传输，保留同一时钟、
驱动和编译优化级别，以分离指令读取开销。结束时恢复原 I-Cache 状态，不修改普通固件配置。
本实验没有开启 D-Cache，也没有启用 DMA，因此不涉及 DMA 与数据缓存的一致性改动。
GDB 读取 Rust 静态变量要使用完整路径
`stm32h750_drivers::display_bench::DISPLAY_BENCH_RESULTS`；仅使用导出的 C 符号名
在 Rust 语言上下文中可能报 `No symbol`。

实板同一测速固件（release `opt-level=1`，400MHz CPU，PLL1_Q=400MHz）结果：

| 测试 | 次数 | 平均耗时 | 换算频率 | 失败 |
|---|---:|---:|---:|---:|
| 清 320×240 帧缓冲（无传输） | 64 | 0.330ms | — | 0 |
| 320×240 整屏传输 | 32 | 129.086ms | 7.75Hz | 0 |
| 三张 98×115 卡片传输 | 64 | 56.888ms | 17.58Hz | 0 |
| 310×14 顶部区域传输 | 128 | 7.309ms | 136.81Hz | 0 |
| 纯色清屏并传输整帧 | 32 | 129.410ms | 7.73Hz | 0 |
| 仅开启 I-Cache 后整屏传输 | 64 | 71.275ms | 14.03Hz | 0 |

SPI2 CFG1=0x20070007，MBR=/8，所以 SCK=50MHz，而非请求的80MHz。
基线 SCB CCR=0x40200（I/D Cache 关闭）；实验为0x60200（仅 I-Cache 开启）。
同一固件内仅开启 I-Cache，整屏传输提升约1.81倍。第一版测试固件的基线约124ms，
与第二版略有差异；关闭指令缓存时编译产生的代码布局也会影响时序，不能混用两版作对照。

50MHz SPI 仅按153,600字节像素数据计算的理想线速上限为40.69帧/秒，不含命令、
打包与软件间隙，也不是面板扫描帧率保证。现有轮询发送路径仍有优化空间，
后续应分别测 DMA 发送、字节打包和真实 UI 绘制，视频还要计入数据读取和解码。
本次仅保留测速入口，完成后重新烧录普通动画/采集固件，未永久改变缓存配置。
恢复固件经 OpenOCD 校验成功；再次命中两次卡片刷新成功断点，采样计数7→8，
时间戳间隔4,999,703µs，气压为 `Fresh`、CPU CFSR=0、SCB CCR恢复为0x40200。
20项主机回归测试、默认配置及测速特性的 Clippy 均通过。

## 14. DMA 像素传输与实板恢复验证（2026-10-11）

第 13 节为改动前的历史基线。当前普通固件永久开启 I-Cache，保持 D-Cache 关闭，
SPI2 改为仅发送；命令保持 8 位，像素切换为 16 位 MSB-first，由 DMA1 stream 0
读取 AXI SRAM。整行区域直接发送帧缓冲（超过 65,535 像素拆两段），窄区域按行复制到
8KB 原生 u16 缓冲，无需逐像素转换为大端字节。纯色矩形使用切片填充。

显示独占整个 DMA1；错误退出先停止 DMA 并执行内存屏障，再允许调用方修改缓冲。
停流超过 1ms 时复位 DMA1。发送等待上限 100ms，SPI 字长切换等待上限 1ms。
CS 在所有返回路径释放，错误后恢复 8 位命令模式；下一次刷新重新设置 DMAMUX 请求。
DMA 缓冲保持不缓存，驱动启动检查 D-Cache 未开启；不能直接开启 D-Cache 或将 DMA1
交给其他外设而不修改所有权、复位策略和缓存维护。

踩坑：第一版把 FEIF 与 TEIF/DMEIF 一律视为失败，导致所有刷新失败。
实板观察到 FEIF 单独置位，DMA 仍可到达 TC，NDTR=0、SPI TXC=1；
单步调试改变启动时序后该现象消失，不能因此认为修好了。
[ST RM0433 的 DMA 错误管理说明](https://www.st.com/resource/en/reference_manual/dm00314099-stm32h742-stm32h743-753-and-stm32h750-value-line-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf)
指出 FIFO 饥饿期间请求不被确认，不会丢 DMA 数据；此处 SPI 为主机，可等待数据继续输出。
驱动因此允许这种暂时的 FEIF，仍检查 TEIF/DMEIF、异常停流，并要求 TC 与线路 TXC
同时完成，否则在期限内返回错误。不能将此策略照搬到不能暂停的接收/从机通道。
检查异常停流时必须先读 EN，再重新读 TC，避免完成恰好发生在两次寄存器读取之间导致误报。

最终测速固件保持 release opt-level=1、400MHz CPU、50MHz SCK，测试期间不暂停：

| 测试 | 次数 | 总成功耗时（µs） | 平均耗时 | 换算频率 | 失败 |
|---|---:|---:|---:|---:|---:|
| 清帧缓冲 | 64 | 12,300 | 0.192ms | — | 0 |
| 320×240 整屏传输 | 32 | 786,706 | 24.585ms | 40.68Hz | 0 |
| 三张 98×115 卡片传输 | 64 | 737,683 | 11.526ms | 86.76Hz | 0 |
| 310×14 顶部区域传输 | 128 | 192,819 | 1.506ms | 663.83Hz | 0 |
| 纯色清屏并传输整帧 | 32 | 792,853 | 24.777ms | 40.36Hz | 0 |

整屏传输约提升 5.25 倍，接近 50MHz SPI 纯像素数据的 24.576ms 理论下限。
局部刷新频率不能当作整屏帧率；上述测试也没有包含视频解码。
普通动画期限由 50ms 调为 16.667ms，往返运动周期仍为 6 秒，传感器仍每 5 秒采样。
原主题与 MADCTL 不变。用户目视确认新驱动颜色、文字与动画显示正常。

实板故障注入：在 DMA 使能前临时将 DMAMUX request 清零，发送走 Timeout 返回；
退出后 DMA EN=0、SPI CFG1=0x20070007（8 位、TXDMAEN=0），PB12 CS 为高、CPU CFSR=0。

该测试验证请求停止后的超时与恢复，不等同于外部 SPI 电气故障或屏幕断线检测。

## 15. 显示与采集代码分层重构（2026-10-11）

根目录的 `transport.rs`、`framebuffer.rs` 实际只是发送/打包辅助函数，而真正的
SPI2、DMA1 和缓冲存储都挤在 `drivers/display.rs`。仅把辅助文件换个目录不能解决
职责混杂，且 `#[path]` 在固件、库和示例中重复挂载实现，会产生重复类型和错误枚举。
本次统一从 `lib.rs` 导出，示例也引用库；AHT20 示例的错误匹配同步改用库的
`Aht20Error`，避免移除路径挂载后仍引用旧局部模块。

最终职责：

| 位置 | 内容 |
|---|---|
| `domain/` | 读数、历史、有效性、通信状态；不依赖 UI/HAL |
| `application/` | 采集生命周期、期限、刷新率、应用主循环和配置 |
| `ui/` | 主题、文字格式化、动画、底栏、脏区域；适配显示刷新接口 |
| `drivers/display/` | ILI9341 协议、绘图、裁剪/打包、DisplayInterface；无 HAL/UI 依赖 |
| `bsp/` | STM32H750 时钟、引脚、I2C 期限、SPI2、DMA1、AXI SRAM |
| `main.rs` | 11 行入口，装配后调用应用循环 |

`DisplayInterface` 必须明确像素源借用和会话结束语义：开始成功后，即使第一个或
中间像素块失败，也必须调用 `finish_pixels`；开始失败则由实现自行清理。新增真正
实例化通用显示驱动的 mock 测试，验证窗口命令、窄区域像素顺序、65,535 像素分段、
失败后的会话结束和重试，不能只测试独立的打包辅助函数。

NOLOAD 缓冲改用 `UnsafeCell<MaybeUninit<_>>` 封装，不使用裸 `static mut`。
一次性领取守卫必须在启动代码会清零的 BSS 中；若把 AtomicBool 一起放进 NOLOAD，
其初值不能得到保证。先用原始指针初始化存储，再生成独占引用。时钟在 BSP 的
`with_board` 栈帧持有，以回调把资源和时钟借用交给应用，避免自引用结构和全局可变时钟。

测速结果也改为 UnsafeCell 包装，GDB 实测可读路径是：
`stm32h750_drivers::bsp::display::bench::DISPLAY_BENCH_RESULTS.0.value`。
`make bench-read` 已同步。移动 profiler 后须编译该特性才能发现旧的 `unused_mut`；
补充 `make check-features` 检查所有特性，不能只检查普通与测速配置。

调试工具踩坑：现有 ST-Link V2 固件为 J18，probe-rs 0.31 要求至少 J26，因此
不能连接。只提供 VID:PID 时还曾走到 Glasgow 后端 panic，完整序列号选择器才能
报告固件过旧。用户明确要求删除 probe-rs 强制限制，继续使用已验证的 OpenOCD/GDB。
AGENTS.md、Makefile 和 Cargo 配置已同步；不需要为这次重构升级调试器固件。

重构后实板测速保持 400MHz CPU、50MHz SCK、仅 I-Cache 开启；未在计时期间暂停：

| 测试 | 成功次数 | 总成功耗时（µs） | 平均耗时 | 失败 |
|---|---:|---:|---:|---:|
| 清帧缓冲 | 64 | 12,300 | 0.192ms | 0 |
| 整屏传输 | 32 | 786,713 | 24.585ms | 0 |
| 三张卡片传输 | 64 | 738,387 | 11.537ms | 0 |
| 顶部区域传输 | 128 | 192,908 | 1.507ms | 0 |
| 清屏并传输整帧 | 32 | 792,865 | 24.777ms | 0 |

结果 status=2，整屏吞吐与第 14 节一致。24 项宿主机测试、默认配置与全特性
Clippy、示例构建均通过。主题颜色与初始化方向值未改动。

完成后用 `make flash` 恢复普通固件，OpenOCD 校验通过。连续四次卡片刷新返回处
